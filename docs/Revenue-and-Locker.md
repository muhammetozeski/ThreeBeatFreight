# Optional revenue and private arena storage

The current published game remains free. Twelve built-in yards, solo contracts, the local rival, real private matches, visual editing, local saving and portable files are not paywalled. The dedicated cloud locker stores three private custom yards per courier for free. Yard Locker Plus raises that capacity to forty; it does not improve movement, energy, matchmaking or scores. Existing cloud yards remain readable, editable and removable when paid capacity ends. A conditional SQL insert enforces the quota even across concurrent saves. Each saved arena is validated using the same bounded arena rules.

## Payment adapter boundary

Polar was selected as a different optional provider from RetryAssurance's Stripe. Its primary [acceptable-use policy](https://polar.sh/legal/acceptable-use-policy) includes games, and its [supported-country list](https://docs.polar.sh/documentation/polar-as-merchant-of-record/supported-countries) includes Turkey. Those policies do not establish approval of this owner or product. No Polar merchant account, real access token, provider sandbox checkout, live charge or webhook delivery has been used in this project. Configuration is absent and public checkout reports unavailable.

The implemented REST adapter pins `Polar-Version: 2026-10`. It uses hosted checkout with the authenticated server courier as `external_customer_id`, a single configured product and a fixed same-origin return address. Browser-supplied customer/product/price identifiers are ignored. Trials and checkout discount codes are disabled for this capacity product. An already active subscription is sent to the billing portal rather than sold another copy. The customer portal is created server-side for the same identity. Returned URLs are restricted to the selected official sandbox or production host.

Paid capacity is checked from the current authenticated [customer state](https://polar.sh/docs/api-reference/customers/state-external), plus a paid and not fully refunded order for the configured subscription/product in its current period. No access is granted from a success redirect or client metadata. Cancel-at-period-end retains capacity until the paid period ends; ended, unpaid or fully refunded coverage does not qualify. Current provider state is read each time additional paid capacity is required. Free new slots and existing read/delete/update operations do not require a working payment provider. Transient provider errors are shown and never represented as successful payment.

The webhook verifies the raw bounded body with Standard Webhooks HMAC-SHA256, message ID, timestamp and a five-minute window. Duplicate IDs are recorded once. Its event journal contains only ID, kind and receive time. It grants no capacity, so duplicate or out-of-order payloads cannot reactivate access; current provider state/order reads decide. New signing secrets follow the post-8-September-2026 scheme described by [Polar's current delivery documentation](https://polar.sh/docs/integrate/webhooks/delivery). Older legacy signing secrets are not supported by this adapter.

`Configure-Revenue.ps1 -Action EnablePolar -BillingMode sandbox` takes credentials from environment variables or masked input, creates/reuses the product, creates a current signed webhook and changes only the selected Cloudflare secret keys. It writes public product/webhook IDs, never credentials. Production requires an actual approved owner account and explicit `-BillingMode production`. The default proposed product is USD 3/month; actual configured product pricing and terms are displayed by Polar before payment. The script's real provider provisioning path has not been executed. Controlled request interception checked its payloads and secret-handling behavior; this is not provider approval or live integration evidence. A provider operation that succeeds before a later configuration error may leave a product or webhook in that account; inspect that account before retrying an uncertain response.

Required owner runtime configuration is `POLAR_ACCESS_TOKEN`, `POLAR_PRODUCT_ID`, `POLAR_WEBHOOK_SECRET`, `POLAR_MODE` (`sandbox` or `production`). The Cloudflare token used by the configuration script stays outside the repository. The script defaults its account/project/site from `docs/hosting.json`. Redeploy current main after changing production settings.

## Advertising adapter

The manual AdSense slot stays unavailable unless the publisher/slot are configured and the owner has separately established a real certified consent-manager installation and set `ADSENSE_CONSENT_READY=true`. Setting publisher IDs alone deliberately leaves that flag false. The public button is not a consent manager and does not certify compliance. There are no publisher placeholders, fabricated ads or sponsor sales. No third-party ad request is made by the default app. If someone who loaded public ads enters a private room, the client performs a full navigation into the room, clearing that script context; it never auto-loads there. The loader consumes the real installed `__tcfapi` addEventListener callback. For applicable TCF traffic it waits for a loaded, completed choice with the required Google vendor/purpose signals and publisher restrictions; unknown/loading/denied signals do not load the ad script. An explicit not-applicable signal from the installed manager is handled separately. Withdrawing the choice clears the loaded script context. No CMP or consent is fabricated by this app. The dynamic ads.txt contains a publisher line only for a configured publisher. Real approval, fill, a certified CMP deployment and revenue have not been tested here.

`Configure-Revenue.ps1 -Action SetAds -AdSenseClient <real-publisher> -AdSenseSlot <real-slot>` configures the selected owner values but keeps consent readiness disabled. The owner must install an actual approved CMP and confirm its real setup before enabling readiness; there is no approval checkbox in the app. `-Action DisableAds` removes only those advertising keys; `-Action DisablePolar` removes only the payment configuration. No existing remote secret map is echoed back into the API. See [AdSense code](https://support.google.com/adsense/answer/9274019) and the owner's actual account policies before enabling it.

## Evidence

68 controlled SQLite/provider-transport assertions passed: free/private quotas, outsider refusal, overwriting existing yards, active paid-period cancellation, full-refund coverage refusal, duplicate purchase refusal, checkout identity, portal host, signature/timestamp rejection, duplicate event recording, no webhook-payload grant and provider failure. Fifteen configuration-script consumer assertions intercepted requests in a disposable copied script and checked product reuse, payload/version, selected-secret-only updates and no credential in public metadata. The first free locker production checks are recorded in Publication.md after deployment. None of these controlled provider responses is a real payment or merchant account.

## Host and body boundaries

API requests are served only from `https://three-beat-freight.pages.dev` unless the owner explicitly configures `SITE_ORIGIN` for a different canonical origin. Current deployment aliases do not expose a second active API. Earlier deployments without that check must be retired separately. Session cookies remain host-bound. POST same-Origin and membership checks remain independent. Request bodies are read with a streaming byte limit; no request is accepted merely because it supplied a small Content-Length.

Seventeen controlled advertising assertions covered the readiness flag and actual loader callback: no request before a usable signal, refusal while the manager UI is shown, ready admission, withdrawal reset and late callback refusal after a match starts. The five loader checks used intercepted browser primitives; no Google request or real consent-manager event was sent. See [Google publisher requirements](https://support.google.com/adsense/answer/13554116) and the [IAB CMP API](https://github.com/InteractiveAdvertisingBureau/GDPR-Transparency-and-Consent-Framework/blob/master/TCFv2/IAB%20Tech%20Lab%20-%20CMP%20API%20v2.md) for the primary specifications. Provider account settings, including Polar's active-subscription policy, remain the owner's actual provider settings; the app does not assert that duplicate subscriptions occur under the provider default.
